# Repository index: the spike's answer

Roadmap B4 asked whether the agent needs a repository index or repo map, and said the question had to
be **measured before it was built**. This is the measurement, from issue
[#308](https://github.com/yusiwen/TinyCode/issues/308), run on 2026-10-28.

## The verdict

**No-go for an injected repo map**, under the condition the issue registered before the run: a map
configuration had to solve at least two more of the six tasks than the baseline without losing one, **or**
hold the solved rate and cut tokens per solved task by ≥ 20%. It did neither — it solved the same six
and raised tokens per solved task by 35%.

Two facts qualify that verdict, and both are in the numbers below:

- **The corpus had no headroom left.** The baseline solved 6/6, so "two more solved" was not reachable on
  this task set no matter how good the map was. The solved-rate branch of the condition could not fire.
- **The cost figure is dominated by one run.** The map arm's *median* run was cheaper and shorter (87k
  tokens and 10 steps, against 116k and 15); its *total* is worse because one `t3-cache` attempt spent
  1.27M tokens over 35 steps. At two repetitions per cell, the mean is not a robust statistic here.

So the answer is not "a repo map is useless". It is: **on the instrument this repository has, an injected
map showed no benefit that survived the corpus's ceiling and the run-to-run spread**, and building an
index would be spending the largest estimate in the roadmap on a case nobody has measured. The condition
for revisiting is at the end.

## What was measured

**The tasks.** Six tasks adapted from the existing tier-2/3 suite, each a small Go module whose defect
spans more than one file, and each **padded with ten unrelated packages** (`internal/metrics`, `configs`,
`logging`, `textutil`, `clock`, `queue`, `retry`, `idgen`, `validate`, `version`) so that finding the
defect means surveying a tree rather than reading two files. The corpus lives in
`eval/spike-repo-index/tasks/`.

| Task | Tier | Defect, as the prompt gives it |
| --- | --- | --- |
| `t2-inventory` | 2 | a refused reservation leaves state behind, across the stock and the order |
| `t2-ledger` | 2 | a refused transfer is not atomic, across the ledger and the account |
| `t2-report` | 2 | wrong output shape and ordering, across the model and the renderer |
| `t3-boundary` | 3 | a half-open window is counted closed, in a helper outside the type |
| `t3-cache` | 3 | expiry at the boundary and refresh on write, across the cache and its clock |
| `t3-extension` | 3 | a conversion is missing, and the existing rounding must not move |

**Why the tests are hidden.** The harness normally copies a task's tests into the work copy and grades
with them. That makes the failing test *localise the defect*: `go test` prints the package and line, so a
repo map's discovery half is measured away. For this spike the work copy carries **no test at all**; the
hidden suite is installed after the run (`-hidden`), so the prompt is the only specification and finding
the code is work. `TestSpikePromptsDoNotNameFiles` fails the build if a prompt names a file.

**The two arms.**

| Configuration | What the agent gets |
| --- | --- |
| `build` | the prompt, and the tree to explore |
| `map` | the same, plus a bounded symbol map of the work copy prepended to the prompt |

The map is generated by the runner (`repoMapDigest`): every non-test Go file, its package, its imports,
and its exported functions, methods and types with signatures — sorted by path, capped at 2000 tokens.
It is a survey, not a capability: the `map` arm gives the model no new tool.

**The run.** 6 tasks × 2 configurations × 2 repetitions = 24 attempts, graded by each task's hidden suite,
metrics read from the run's own trajectory. Model `deepseek-flash`, one machine, 2026-10-28.

The median row is the one that says anything nice about the map: cheaper and shorter runs, which is what
"a survey replaces exploration" would look like. The total is the one the pre-registered condition names,
and it says the opposite, because of the single 35-step attempt. **Both are reported because either
alone is misleading.**

## What the spike does not answer

- **Whether a *callable* index helps.** The tool-surface arm (query for definitions and references across
  the tree — the LSP `workspace/symbol` and call-hierarchy route) was not built. The issue's method named
  three configurations; this ran two, and the narrowing is recorded here rather than discovered later.
  A tool that answers one question at a time is a different treatment from 2000 tokens of map in every
  prompt, and its cost profile is the opposite: paid per use instead of per run.
- **Whether an index helps on a real repository.** These modules are twenty to thirty files. The larger
  the tree, the more a map should matter — and the harder it is to build a task whose hidden suite is
  fair.
- **Whether the map's shape was right.** Symbols and imports, capped at 2000 tokens, no ranking. A map
  that ranked files by relevance to the prompt (which is what the memory store's vector machinery could
  do) was not tried.

## When to revisit

Reopen B4 when **all** of these hold:

1. the corpus can defeat the baseline — at least two of its tasks must fail `build` today, or the
   solved-rate branch of this experiment cannot fire;
2. repetitions are at least three per cell, so the mean is not one attempt's anecdote;
3. the treatment is the **tool surface**, not the injected map: the map arm is measured and lost.

If the tool arm also fails those tasks, the entry stays closed with this document as its answer, and the
"largest bet in the roadmap" is recorded as not worth the bet.

## Reproducing

```bash
make build
cp bin/tinycode /tmp/tinycode-under-test     # see the note below
TINYCODE_EVAL=1 go run ./eval/runner \
  -tasks eval/spike-repo-index/tasks \
  -hidden eval/spike-repo-index/hidden \
  -configurations build,map -reps 2 \
  -out /tmp/spike-out -work /tmp/spike-work \
  -binary /tmp/tinycode-under-test
```

`go test ./eval/runner` proves the corpus offline: every spike task is red with its hidden suite
installed and green after its reference solution, the work copies carry the padding, and the prompts name
no file. None of that needs a provider.

**Why the binary is copied out of the tree.** On this machine, executing `bin/tinycode` in place fails
every provider call (`dial tcp …: connect: bad file descriptor`, or an i/o timeout) while a byte-identical
copy at `/tmp/tinycode-under-test` succeeds. The cause is outside this repository (the agent harness's
sandboxing of that path); the copy is the workaround, and the September release binary in `bin/` behaves
the same way in place.
