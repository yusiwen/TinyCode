# Language

The interface can be shown in English or Simplified Chinese. English is the source
language: every message is written once, in English, in the code that shows it, and
a translation is an entry keyed by that text. A message with no entry stays in
English, so an incomplete catalogue degrades to a readable screen rather than to a
key name.

```console
$ tinycode --lang zh --list-sessions
没有已保存的会话。

$ TINYCODE_LANG=zh tinycode --list-sessions
没有已保存的会话。
```

## Choosing the language

The first supported value wins, in this order:

1. `--lang` on the command line;
2. `language` in `~/.tinycode/config.json` or `./.tinycode/config.json`;
3. `TINYCODE_LANG`;
4. `LC_ALL`, then `LC_MESSAGES`, then `LANG`.

Accepted spellings are the ones people actually write: `en`, `english`, `zh`,
`chinese`, and the locale forms `en_US.UTF-8`, `zh_CN.UTF-8@euro`, `zh-Hans-CN`.
`C` and `POSIX` mean English, because that is how a shell says "no translations".
A value that names no supported language is **skipped, not fatal**: a typo in
`LC_ALL` cannot lock someone out of the language their `LANG` asks for.

An unparsable value that is the only one set leaves the interface in English.

## What is translated

Everything the program shows a person while it runs:

- the TUI: status bar, system messages, dialogs and their answers, the welcome
  banner, the command palette's descriptions, key hints, `/help`;
- the command line: `--list-sessions`, `--export-session`, `--undo`,
  `--list-grants`, `--trajectories`, and the confirmations they print;
- desktop notifications.

## What is not translated, and why

These boundaries are deliberate; each one would make the product worse if crossed.

- **`--help` and flag descriptions.** Cobra renders them before the command body
  runs, so the configured language is not known yet. A half-translated `--help` is
  worse than an English one, and the English one is what the documentation and the
  issue tracker quote.
- **Error strings and log lines.** They are diagnostics: they name file formats,
  provider routes and configuration keys, and they are quoted verbatim in bug
  reports. A translated error that nobody can search for is a support cost, not a
  kindness. (The *frames around* them — "Error: %v" — are translated.)
- **Model-facing text.** System prompts, tool descriptions and tool results are
  read by the model, not by a person. Translating them changes what the agent does,
  not what the user sees, and it would make prompts and tests depend on the UI
  language.
- **Values that persist.** A grant recorded as `Always allow` in the config file is
  data, not a label; it is written and compared in English whatever the interface
  language is.

## Using it in code

```go
import "github.com/yusiwen/tinycode/i18n"

m.ShowStatus(i18n.T("No agent available"))
m.appendSystem(i18n.T("Compressed: %d messages remaining", remaining))
```

`T` formats with `fmt.Sprintf` only when arguments are passed. That is what keeps a
message that legitimately contains a percent sign ("100% local") from becoming
`%!d(MISSING)`, and it is why messages that take arguments always pass them.

Rules that follow from the design:

- **The English text is the key.** Editing a message means editing its catalogue
  entry too; the gate below fails until the two agree.
- **A table that is translated at draw time** — the command palette, the welcome
  rows, the key hints, the permission answers — passes its English text to `T` when
  it is drawn, not when the package is initialised: the language is chosen in
  `main`, after package variables already exist. `TestTheLanguageSwitchChangesWhatTheInterfaceDraws` is the guard against getting this wrong.
- **The permission dialog compares strings.** "Always allow" is recognised with
  `strings.HasPrefix` against the translated prefix, so the translated full label
  must begin with it. `TestThePermissionPrefixesAgree` enforces that.

## The gates

Three tests keep the catalogue honest, and each was mutation-checked when it was
written (a dropped entry, a swapped verb, an unwrapped call).

- `i18n/catalogue_test.go` scans every `i18n.T("…")` call in the module and fails
  when a message has no Chinese entry, when a catalogue entry is mentioned by no
  source file, or when a translation's **verb sequence** differs from its message's
  — a `%d` that became `%s` passes a count and renders `%!s(int=3)`.
- `i18n/coverage_test.go` fails when a literal is handed straight to a sink —
  `ShowStatus`, `appendSystem`, `showDialog`, `showDialogWithCancel` — instead of
  through `T`.
- `tui/i18n_test.go` reads the tables that reach `T` through a variable and checks
  their entries, then switches the language and asserts the drawn banner changes.

Scenario runs pin `TINYCODE_LANG=en` (`make test-tui-scenarios`, and the PTY smoke
in `tui/verification_test.go`), so a developer whose locale is Chinese runs the same
screenshots as everybody else. `tui/testdata/scenarios/i18n-zh.scenario` is the
end-to-end proof the other way round: it starts the real binary with
`TINYCODE_LANG=zh` and waits for the Chinese banner on a real terminal.

## Limits

- The committed screenshots are English. The pure-Go PNG renderer has no CJK glyphs, so a Chinese
  screenshot needs a font that has them: `tuiprobe shot --font /path/to/CJK.ttf`. The terminal itself
  draws the glyphs — `tuiprobe text` prints the screen correctly — only the image needs the font.

- No plural rules and no per-message context: both languages get by without them
  today, and a language that needs them would need more than this mechanism.
- Numbers, dates and currency are formatted as the code already formatted them
  (the status bar's `tokens: 1,234` is a counter, not prose).
- Two languages only. `Parse` returns "not supported" for anything else, which is
  what lets `Detect` skip a value instead of failing.
